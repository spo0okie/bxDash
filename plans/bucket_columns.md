# Канбан-раскладка с персональными столбцами (как «Мой план» в Битрикс24)

Отдельная раскладка персональной доски: вместо календарной сетки — классический
канбан, где задачи вручную раскладываются по произвольным столбцам. Набор
столбцов у каждого пользователя свой. Механизм повторяет «Мой план» актуального
Битрикс24: стадии принадлежат пользователю, задача лежит в стадии *в плане
конкретного пользователя*, одна и та же задача может быть в разных стадиях у
разных людей.

Статус: **этапы 1–7а готовы и проверены на портале**. Этап 8 реализован по диагностике Bitrix 24.300.200; проверен локальными контрактными тестами, проверка записи на целевом портале остаётся. См. docs/bitrix-kanban.md. План составлен 2026-09-12, UI-часть переписана 2026-10-03.

## Задача (что хотели)

Долгий ящик с тремя приоритетами удобен, но недостаточен. Нужны произвольные
столбцы: «Ожидание», «На проверке», «Ближние», «Дальние» и т.п. Типы столбцов
не фиксируются. Столбец — ручная группировка, **никакой автоматики по статусу
Битрикса** (задача «ждёт подтверждения» может сознательно лежать в «В работе»).

## Принятые решения

Данные (обсуждение 2026-09-12):

1. Набор столбцов **у каждого пользователя свой** (как «Мой план»).
2. Привязка хранится на пару **элемент + пользователь-владелец доски**.
3. Отсутствие явной привязки — это тоже столбец: у каждого пользователя есть
   ровно один столбец **по умолчанию**, куда попадает всё непривязанное.
   При создании он называется **«Входящие»**, переименовать можно.
4. Порядок внутри столбца — существующий общий `sorting` (`XML_ID`/`SORT`).
   Он общий с календарём: перестановка в канбане меняет порядок и в ячейке
   календаря. Персональный порядок не делаем.
5. Хранилище: **своя таблица** в бэкенде bxDash (штатных `b_tasks_stages` на
   текущем портале нет). Определение столбцов и привязок вынесено в
   слой-провайдер, чтобы на актуальном Битриксе подменить его на штатные
   таблицы модуля tasks без правок остального кода.

Интерфейс (обсуждение 2026-10-03):

6. Столбцы категорируют **все открытые задачи**, а не только долгий ящик.
   Совмещать в одной сетке ось времени и ось столбцов не будем: данные
   получаются разреженными, а канбан нужен, чтобы видеть всё разом.
7. Канбан — **отдельная раскладка** рядом с календарной, переключатель
   «календарь / канбан». Оси времени в канбане нет.
8. Канбан доступен только в **персональном режиме** (выбран один пользователь)
   и показывает доску выбранного пользователя. Общая доска остаётся календарём.
9. Завершённые не копятся: их количество ограничено глубиной загрузки истории
   (те же «недели назад», что в календаре).
10. Время в канбане живёт **на карточке**: отсчёт до плановой даты нейтральным
    цветом, по образцу красного отсчёта до крайнего срока.
11. Двигать сроки из канбана — через контекстное меню: к «Отодвинуть срок»
    добавляется «Приблизить срок» с теми же интервалами.
12. Календарная раскладка, три приоритета долгого ящика и штатное `PRIORITY`
    **не трогаются**. Нужны ли они после появления канбана, решим позже.

## Как это устроено в актуальном Битрикс24 (ориентир для провайдера №2)

Проверить по коду модуля `tasks` целевого портала перед миграцией, но
ожидаемая картина такая:

- `b_tasks_stages` (`\Bitrix\Tasks\Kanban\StagesTable`): `ID`, `TITLE`,
  `SORT`, `COLOR`, `SYSTEM_TYPE` (`NEW` у стадии по умолчанию, иначе пусто),
  `ENTITY_ID`, `ENTITY_TYPE` (`U` — личный план пользователя, `P` — временная шкала, `G` — группа).
- `b_tasks_task_stage` (`\Bitrix\Tasks\Kanban\TaskStageTable`): `TASK_ID`,
  `STAGE_ID`. Задача может иметь по одной строке на план каждого
  пользователя. Отсутствие строки в плане = стадия `SYSTEM_TYPE=NEW`.
- Стадии личного плана создаются лениво при первом обращении
  (`StagesTable::getStages($userId)` с `ENTITY_TYPE=U`).

Наша своя схема (ниже) намеренно изоморфна этой, чтобы провайдер для
нового портала был тонкой обёрткой над ORM tasks.

## Архитектура

### Бэкенд (`back/`)

Новый слой **провайдера стадий** и один контроллер поверх него.

```
back/app/models/
  stages_provider.php            интерфейс (абстрактный класс)
  stages_provider_table.php      реализация на своих таблицах (этот портал)
  stages_provider_bitrix.php     реализация на b_tasks_stages (потом, новый портал)
back/app/ctl/
  controller_stage.php           REST: список/создание/правка/удаление/перенос
back/conf.php
  $stagesProvider = 'table';     выбор реализации
```

Интерфейс `stages_provider` (все id — int, itemType — `'task'|'job'|'ticket'`):

| Метод | Назначение |
|---|---|
| `getStages($userId)` | список стадий пользователя, отсортированный по `SORT`; если у пользователя стадий нет — создаёт единственную стадию по умолчанию «Входящие» и возвращает её |
| `getDefaultStageId($userId)` | id стадии по умолчанию |
| `createStage($userId, $title, $color, $sort)` | новая стадия |
| `updateStage($id, $fields)` | `TITLE`, `COLOR`, `SORT` |
| `deleteStage($id, $moveToId)` | удалить стадию, перевязав элементы на `$moveToId` (по умолчанию — стадия по умолчанию). Стадию по умолчанию удалять нельзя |
| `reorderStages($userId, array $idsInOrder)` | переписать `SORT` пачкой |
| `getItemStages($itemType, array $itemIds)` | `[itemId => [userId => stageId, ...]]` для пачки элементов |
| `setItemStage($itemType, $itemId, $userId, $stageId)` | привязать; `$stageId === null` — снять привязку (элемент падает в стадию по умолчанию) |
| `removeItem($itemType, $itemId)` | убрать все привязки элемента (при удалении элемента) |

Реализация `stages_provider_table` — две таблицы (создаются методом
`install()` провайдера, вызов через `stage/install` один раз):

```sql
CREATE TABLE bxdash_stage (
  ID         INT AUTO_INCREMENT PRIMARY KEY,
  USER_ID    INT NOT NULL,
  TITLE      VARCHAR(255) NOT NULL,
  SORT       INT NOT NULL DEFAULT 100,
  COLOR      VARCHAR(7) NULL,
  IS_DEFAULT CHAR(1) NOT NULL DEFAULT 'N',
  INDEX ix_user (USER_ID, SORT)
);
CREATE TABLE bxdash_item_stage (
  ITEM_TYPE  VARCHAR(16) NOT NULL,
  ITEM_ID    INT NOT NULL,
  USER_ID    INT NOT NULL,
  STAGE_ID   INT NOT NULL,
  PRIMARY KEY (ITEM_TYPE, ITEM_ID, USER_ID),
  INDEX ix_stage (STAGE_ID)
);
```

`USER_ID` в `bxdash_item_stage` избыточен (стадия и так принадлежит
пользователю), но даёт уникальность «один элемент — одна стадия в одном
плане» на уровне БД. В реализации на `b_tasks_task_stage` уникальность
обеспечивается кодом, как в Битриксе.

Работа с БД — через `$DB->Query()` Битрикса (PHP 5 совместимость, как во
всём `back/`). Работы (`job`) и заявки (`ticket`) в `b_tasks_task_stage`
не лягут; провайдер для нового портала хранит задачи в штатных таблицах,
а `job`/`ticket` — в `CUserOptions` (`bxdash_kanban/native_board`). Это внутреннее дело
провайдера, фронт различий не видит.

### REST (`controller_stage`)

| Запрос | Тело / параметры | Ответ |
|---|---|---|
| `GET stage/list/{userId}` | | `[{ID, USER_ID, TITLE, SORT, COLOR, IS_DEFAULT}]` |
| `POST stage/create` | `{user, title, color?, sort?}` | `{result:'ok', id, stage}` |
| `POST stage/update/{id}` | `{title?, color?, sort?}` | `{result:'ok', id, stage}` |
| `POST stage/delete/{id}` | `{moveTo?}` | `{result:'ok', id, movedTo}` |
| `POST stage/reorder` | `{user, ids:[...]}` | `{result:'ok', stages}` |
| `GET stage/install` | | создаёт таблицы (идемпотентно) |

Ошибки — `{result:'error', error}` с кодом: 409 — «так нельзя» (пустое
название, плохой цвет, чужой столбец, удаление столбца по умолчанию),
404 — столбец или пользователь не найден, 401 — нет авторизации,
500 — ошибка БД (в том числе «таблиц нет», если не выполнен `stage/install`).
`color: null` в `update` сбрасывает цвет.

Права: как везде в bxDash — любой авторизованный пользователь портала.
Отдельной проверки «свой план / чужой план» не делаем: дашборд командный,
перекладывать чужие задачи уже можно.

### Изменения существующих контроллеров

- `controller_task`, `controller_job`, `controller_ticket`:
  - в выдаче `load`/`get`/`linked` к каждому элементу добавляется поле
    `STAGES` — объект `{userId: stageId}` из `getItemStages()` одним запросом
    на пачку;
  - в `action_update` новые параметры `stage` (id или `null`) и `stageUser`
    (владелец доски). Если пришли оба — `setItemStage()`. Остальные параметры
    без изменений, в том числе `priority`;
  - в `action_create` те же два параметра, привязка после создания.
- Удаление элемента (если оно есть в контроллере) — вызывать `removeItem()`.
  Привязки-сироты безвредны: фронт относит элемент с неизвестной стадией к
  столбцу по умолчанию.
- Ошибки: исключения ловит `router.php` и отдаёт `{"result":"error",...}`.
  За «нельзя» (удаление столбца по умолчанию, чужая стадия в `moveTo`) —
  **409**, не 401/403: их `BackendSystem.fetch` принимает за слёт авторизации.

Миграция данных не нужна: приоритеты остаются в календаре как были, а первый
столбец каждого пользователя создаётся лениво при первом `getStages()`.

## Интерфейс

### Переключение раскладки

- Новый ключ в `LayoutStore.PREF_DEFAULTS`: `kanban: false`, геттер и
  `setKanban()` по образцу остальных (нужно для `MenuButton`).
- Канбан активен, когда `users.selected !== null && layout.kanban`. Computed
  `layout.kanbanActive`, чтобы условие не размазывалось по компонентам.
- Кнопка `<MenuButton property='kanban' …/>` в [Layout.jsx](../src/Components/Layout/Layout.jsx)
  рядом с кнопкой `expand`, видна только в персональном режиме. Кнопка
  `expand` при активном канбане скрывается (оси времени нет).
- В `Layout.jsx` при `kanbanActive` вместо `div.dashBoard › CalendarGrid` и
  `RightPaneBucket` рендерится `KanbanBoard`. `AppHeader` (выбор пользователя),
  sidebar с заметками, поиск, модалки — без изменений.
- Выход из персонального режима возвращает календарь сам собой; значение
  `kanban` при этом сохраняется, и при следующем выборе пользователя снова
  откроется канбан.

### Раскладка E — канбан

```
div.layout
├─ Sidebar (memosVisible)
└─ div.kanbanBoard                     горизонтальная прокрутка
   ├─ div.kanbanColumn  × N            стадии владельца в порядке sort
   │  ├─ div.kanbanColumnTitle         липкий заголовок: название, счётчик, меню
   │  └─ div.kanbanColumnBody          вертикальная прокрутка столбца
   │     ├─ CreateItemButton
   │     └─ CardsBlock (dnd)           открытые элементы стадии
   ├─ div.kanbanColumn.closed          системный столбец «Завершённые»
   │  └─ CardsBlock (без dnd)
   └─ button.kanbanAddColumn           «+ столбец»
```

- Ширина столбца фиксированная (как неделя-колонка в раскладке D, 200px,
  вынести в CSS-переменную). Столбцов может быть 1…20, поэтому доска
  прокручивается по горизонтали, а каждый столбец — по вертикали сам.
- Столбец можно **свернуть** в узкую полоску: название вертикально и счётчик.
  Список свёрнутых — ключ `kanbanCollapsed` (массив id стадий) в `prefs`.
- Цвет стадии (`stage.color`) — заливка заголовка и рамка столбца (и свёрнутой
  полоски); цвет текста подбирается по контрасту (`kanbanColor.jsx`). Сначала
  была только полоска над заголовком — оказалась слишком незаметной.
- Карточки — те же `TaskCard` / `JobCard` / `TicketCard`, новых не делаем.

Новые файлы в `src/Components/Layout/Kanban/`: `KanbanBoard.jsx`,
`KanbanColumn.jsx`, `KanbanColumnTitle.jsx`, `Kanban.css`.

### Что попадает на доску

Владелец доски — `users.selected`.

- **Открытые** задачи, работы и заявки, где владелец — ответственный. При
  включённом `accomplicesVisible` — ещё и задачи, где он соисполнитель
  (приглушённые, как в календаре). Типы подчиняются существующим флагам
  `tasksVisible` / `jobsVisible` / `ticketsVisible`. Планы на доску не идут.
- Независимо от даты: и запланированные на эту неделю, и те, что в работе, и
  лежащие в долгом ящике. Дозагрузка не нужна — `loadItems(from, null)` уже
  тянет все открытые.
- Столбец элемента — `item.stageFor(owner)`. Если привязки нет или стадия
  не найдена среди стадий владельца — столбец по умолчанию.
- Сортировка в столбце — `dashItemsSort`, как в ячейке календаря.
- **«Завершённые»** — системный столбец, крайний справа, не из таблицы стадий:
  закрытые элементы владельца с датой закрытия не раньше
  `time.firstWeekStart()`, сортировка `dashClosedItemsSort`, без
  перетаскивания, по умолчанию свёрнут. Привязка к стадии при закрытии не
  стирается: задача, возвращённая в работу, ложится в прежний столбец.

### Перетаскивание

Ячейка канбана — объект того же вида, что в календаре, с флагом раскладки:

```js
{ id: 'kanban/' + stage.id, kanban: true, user: owner, stage,
  t: null, dropT: null, maxSorting, minSorting, dragOver }
```

- `DndHelper.buildMoveParams`: если целевая ячейка `kanban` — в параметры идут
  только `sorting` и, при смене столбца, `stage` + `stageUser`. **Дата и
  ответственный в канбане перетаскиванием не меняются** (иначе перенос
  задачи соисполнителя переназначал бы её на владельца доски).
- Вычисление нового `sorting` (`computeNewSort`) — без изменений.
- Столбец регистрируется как drop-цель по образцу `UserCell`.
- Создание через `CreateItemButton` в столбце: элемент без плановой даты
  (как в ячейке долгого ящика) с `stage`/`stageUser` этого столбца.

### Управление столбцами

Меню в заголовке столбца (antd `Dropdown`):

- переименовать (то же по двойному клику, правка на месте);
- цвет;
- ~~сдвинуть влево / вправо~~ — заменено перетаскиванием столбцов, см. этап 7а;
- свернуть;
- удалить — с выбором, куда перенести задачи; для столбца по умолчанию пункт
  недоступен, но переименовать его можно.

Кнопка «+ столбец» в конце доски создаёт стадию и сразу включает правку
названия.

### Карточка: отсчёт до плановой даты

Сейчас `DeadlineCountdown` в [TaskCard.jsx](../src/Components/Items/ItemCards/Task/TaskCard.jsx)
рисует поверх карточки крупный отсчёт до крайнего срока цветом
`--sem-danger`. В канбане добавляется второй, нейтральный:

- `TaskItem.planRemainingMs` (computed): время до `startDatePlan`. `null`,
  если задача закрыта, даты нет или она уже прошла.
- Компонент `PlanCountdown` рендерится **только при `layout.kanbanActive`**:
  в календаре плановую дату показывает само положение карточки.
- Если у задачи есть и крайний срок, и плановая дата — показывается только
  красный отсчёт до крайнего срока, плановая дата уходит в подсказку.
- Формат — `TimeHelper.strRemaining`. Плановая дата хранится с точностью до
  дня, поэтому пересчёт привязать к `time.today` или минутному тику, а не к
  посекундному `time.strTime`, чтобы вся доска не перерисовывалась раз в
  секунду.
- Цвет — новый токен `--countdown-neutral` в
  [tokens.css](../src/Themes/modern/tokens.css): в светлой теме темнее фона
  карточки, в тёмной — светлее. Класс `span.planCountdown` наследует
  геометрию `span.deadlineCountdown`.

Нейтральный отсчёт — **только у задач**. У заявок уже есть свой отсчёт SLA
(`SlaCountdown` в `TicketCard.jsx`, не показывается у отложенных), в канбане
он работает как есть. Работам отсчёт не нужен.

### Контекстное меню

В `ItemsMultiStore.contextMenu` / `contextMenuHandler`:

- **«Приблизить срок»** — новое подменю рядом с «Отодвинуть срок», те же
  интервалы: 1 неделя, 2 недели, 1 месяц, 2 месяца. Пункт активен, только
  если после сдвига дата не окажется раньше сегодня:
  `item.t - interval >= time.today`. Недоступные пункты **приглушены**
  (`disabled`), а не скрыты, чтобы меню не прыгало. Пример: задача через
  3 недели — «на 1 неделю» и «на 2 недели» активны, оба «месяца» приглушены.
  Если плановой даты нет или задача закрыта — приглушено всё подменю.
- **«В столбец»** — подменю со стадиями владельца ячейки (`cell.user`),
  текущая отмечена. Работает в обеих раскладках: в календаре это единственный
  способ переложить задачу в другой столбец, не переключаясь в канбан.
- «В начало списка» / «В конец списка» работают от `cell.maxSorting` /
  `cell.minSorting`, ячейка канбана их предоставляет.
- «В долгий ящик → на верх / на дно» в канбане оставляем: снять плановую дату
  оттуда тоже бывает нужно.

Меню и обработчик уже общие для всех раскладок, отдельного меню для канбана
не заводим.

## Фронт: данные

**`StagesStore`** (`src/Data/Stores/StagesStore.jsx`), создаётся в
`createStores()`:

- `byUser: observable.map(userId → Stage[])`, `Stage = {id, userId, title,
  sort, color, isDefault}`.
- `load(userId)` — `GET stage/list/{userId}`; ленивая загрузка при первом
  `stagesOf(userId)`.
- `stagesOf(userId)`, `defaultStageOf(userId)`, `stageById(id)`.
- `create / update / remove / reorder` — оптимистично меняют список, шлют
  REST, по ответу перечитывают, рассылают WS-событие `stageUpdate {userId}`.
  Обработчик события в `WsStore` → `load(userId)`.
- `board` (computed) — **один проход** по открытым и закрытым элементам
  владельца: `{ byStage: Map(stageId → items[]), closed: items[] }`.
  Столбцы только читают свою долю (тот же принцип, что `PeriodItem.itemsByUser`).
- Каждая ветка ошибки — `notify.error` с причиной, успех создания и удаления
  столбца — `notify.success`.

**`DashItem`**:

- поле `stages` (`observable.map(userId → stageId)`), заполняется из
  `item.STAGES` в базовом `loadData()`;
- `stageFor(userId)` — явная привязка либо id столбца по умолчанию;
- `update({stage, stageUser})` кладёт значение в `stages`, `save()` передаёт
  оба параметра в бэк как есть.

**`TaskItem`**: `planRemainingMs` (см. отсчёт выше).

Фронт не знает, где хранятся стадии: он работает только с `stage/*` и полем
`STAGES`. Это и есть точка подмены для нового портала.

### Этап 7а. Стопки: столбцы друг под другом — готов, проверен на портале 2026-10-04

Запрос после этапа 7: небольшой столбец (например «В работе») не должен занимать
всю высоту доски. Решения пользователя: переставлять столбцы и по горизонтали, и
по вертикали перетаскиванием (тем же механизмом, что карточки); граница между
столбцами стопки подвижная, высоты хранятся локально, пока границу не двигали —
поровну.

Модель: доска — ряд **стопок**, в стопке один или несколько столбцов сверху вниз.
Хранится плоско: порядок (`SORT`) и признак `STACKED` — «стою под предыдущим».

Сделано:
- Бэкенд: колонка `STACKED` в `bxdash_stage` (доращивается сама при первом
  обращении к таблице старого образца), поле `STACKED` в выдаче,
  `stage/reorder` принимает `stacked: [id…]`. Без этого параметра раскладка по
  стопкам не трогается. При удалении верхнего столбца стопки следующий
  становится верхним, а не уезжает в стопку слева.

  `moveInStacks`, `dropEdge`, `resizeWeights`.

- `KanbanStack.jsx` — стопка и подвижная граница; `KanbanColumn` — столбец
  перетаскивается за название (свёрнутый — за всю полоску).
- Куда встанет столбец, решает место броска на столбце-цели: крайние четверти
