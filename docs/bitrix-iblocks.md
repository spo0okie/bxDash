# Инфоблоки работ (jobs), планов (plans) и заметок (memo)

Инструкция для ручной настройки нового портала. Код bxDash не создаёт эти
инфоблоки и свойства автоматически. Перед созданием согласуйте их с владельцем
портала. Для работы API требуется установленный модуль Bitrix «Информационные
блоки» (`iblock`); `back/api.php` подключает его явно.

## 1. Создание инфоблоков

В административной части откройте **Контент → Инфоблоки → Типы инфоблоков → Сервисы**.
Создайте в нём три инфоблока:

| Назначение | Название, например | Символьный код, например |
| --- | --- | --- |
| jobs | Работы bxDash | `bxdash_jobs` |
| plans | Планы bxDash | `bxdash_plans` |
| memo | Заметки bxDash | `bxdash_memos` |

Все три инфоблока сделайте активными и привяжите к сайту нужного портала.
Тип, название и символьный код можно выбрать свои: API обращается по числовому ID.
Сохраните инфоблоки и запишите присвоенные Bitrix ID из списка или формы редактирования.

Разделы, ЧПУ и шаблоны публичных страниц для bxDash не требуются. Не включайте
обязательность картинок, символьного кода, детального текста или иных полей,
которые API не заполняет. Дата окончания активности должна допускать пустое значение.
Не задавайте автоматическую дату окончания: bxDash использует её как дату закрытия.

## 2. Свойства

На вкладке **Свойства** создайте следующие свойства. **Коды должны совпадать
точно, включая регистр**. Все свойства активные, одиночные (не множественные),
не обязательные, без описания значения.

### Работы (jobs)

| Код | Название | Тип | Значения |
| --- | --- | --- | --- |
| `USER` | Ответственный | Привязка к пользователю (`S`, `USER_TYPE=UserID`) | ID сотрудника Bitrix |
| `PRIORITY` | Приоритет | Число (`N`) | `0` — низкий, `1` — обычный, `2` — высокий; |

### Планы (plans)

| Код | Название | Тип | Значения |
| --- | --- | --- | --- |
| `USER` | Ответственный | Привязка к пользователю (`S`, `USER_TYPE=UserID`) | ID сотрудника Bitrix |
| `STATUS` | Выполнение | Число (`N`) | `0` — не выполнено, `1` — частично, `2` — выполнено; по умолчанию `0` |
| `AUTHSTATUS` | Согласование | Число (`N`) | `0` — ещё не согласовано, `1` — согласовано, `2` — отказано; по умолчанию `0` |
| `AUTHORIZED` | Кто согласовал | Привязка к пользователю (`S`, `USER_TYPE=UserID`) | Заполняется API; по умолчанию пусто |
| `AUTHDATE` | Дата согласования | "Дата/Время" (`DateTime`) | Заполняется API; по умолчанию пусто |

Типы свойств Bitrix описаны в [официальной документации](https://www.dev.1c-bitrix.ru/api_help/iblock/fields.php?print=Y).

### Заметки (memo)

Для заметок **дополнительные свойства не нужны**, в том числе `USER`.
Текст хранится в стандартном поле `DETAIL_TEXT` как обычный текст;
при создании первая строка записывается в `NAME`. Автор — стандартное поле
`CREATED_BY`, которое API заполняет ID текущего пользователя Bitrix.

`DATE_ACTIVE_FROM` содержит дату заметки, `DATE_ACTIVE_TO` — дату закрытия
(у открытой заметки поле пустое), `SORT` — порядок. Эти поля уже существуют
у элементов инфоблока, создавать для них свойства не нужно. Оставьте
`PREVIEW_TEXT`, картинки и остальные неиспользуемые поля необязательными;
для `DETAIL_TEXT` не задавайте HTML по умолчанию или обязательную обработку.

Заметки личные: выборка периода не зависит от выбранного сотрудника доски.
Чтение по ID, изменение и удаление также ограничены текущим автором и
настроенным инфоблоком. Даже администратор через `memo/*` работает со своими
заметками; административный интерфейс Bitrix имеет собственные права доступа.

### Стандартные поля элементов

Создавать отдельные свойства для этих данных не нужно:

| Поле Bitrix | Использование bxDash |
| --- | --- |
| `NAME` | Заполняется заголовком при создании |
| `PREVIEW_TEXT` | Текст работы или плана, обычный текст |
| `DETAIL_TEXT` | Комментарий к плану или полный текст заметки, обычный текст |
| `DATE_ACTIVE_FROM` | Срок работы / дата плана |
| `DATE_ACTIVE_TO` | Дата закрытия; пусто — элемент открыт |
| `SORT` | Порядок карточек |
| `CREATED_BY`, `MODIFIED_BY` | Автор и редактор |

Срок плана задаёт интерфейс, план нельзя создавать в «долгом ящике».
Для jobs отсутствие срока допустимо.

## 3. ID в серверной конфигурации

В **каталоге API**, рядом с `api.php`, создайте `conf.php` по образцу
[`back/conf.example.php`](../back/conf.example.php). В существующий `conf.php`
добавьте только недостающие определения, сохранив остальные настройки:

```php
<?php
// Пример: заменить на ID из вашей административной части Bitrix.
define('BXDASH_JOB_IBLOCK_ID', 120);
define('BXDASH_PLAN_IBLOCK_ID', 121);
define('BXDASH_MEMO_IBLOCK_ID', 122);
```

Укажите разные положительные целые ID существующих инфоблоков. Допустимы
числа и строки из цифр без ведущего нуля. Значений ID по умолчанию нет.
Отсутствующее определение или некорректное значение вызывает JSON-ошибку
HTTP 500 с именем настройки; существование инфоблока и состав свойств нужно
проверить вручную. Перед обновлением действующего портала обязательно задайте
все три ID явно. Обновление и удаление отклоняются с HTTP 409, если элемент
не принадлежит настроенному инфоблоку.

Эти настройки читает backend при запросах; они не относятся к
`public/config.priv.js` или `portal.config.php`. Пересборка React при смене ID
не требуется. Конфиг `back/conf.php` исключён из Git; сохраняйте его при
обновлении API. Vite собирает фронтенд в `build/`, каталог `back/` нужно
публиковать отдельно по адресу API, заданному во фронтенде.

## 4. Доступ и проверка после развёртывания

Выдайте нужным группам сотрудников доступ к этим инфоблокам согласно политике
портала; для редактирования через админку нужны права изменения. Не открывайте
запись анонимным посетителям. Права инфоблока сами по себе не заменяют проверку
доступа в API: текущие контроллеры вызывают низкоуровневые методы
`CIBlockElement`. Для jobs/plans нет отдельной проверки владельца каждого
элемента; для memo проверяется `CREATED_BY` текущего пользователя.

Под обычной учётной записью сотрудника:

1. Создайте работу на сегодня и план на текущую неделю. Проверьте в админке,
   что элементы появились именно в указанных инфоблоках, а `USER` содержит ID сотрудника.
2. Перезагрузите dashboard: обе карточки должны загрузиться снова.
3. У работы поменяйте срок, ответственного и приоритет, закройте и откройте её.
   После перезагрузки проверьте сохранённые значения.
4. У плана измените текст, под администратором согласуйте его, добавьте комментарий
   и смените состояние выполнения. Перезагрузите страницу и проверьте свойства
   `STATUS`, `AUTHSTATUS`, `AUTHORIZED`, `AUTHDATE` и поле `DETAIL_TEXT` в админке.
5. Удалите тестовые карточки и убедитесь, что удалены соответствующие элементы.
6. Создайте заметку в боковой панели, проверьте в новом инфоблоке `DETAIL_TEXT`
   и `CREATED_BY`. Измените текст и перезагрузите dashboard — он должен сохраниться.
   Под другой учётной записью заметка не должна появляться; прямые запросы
   изменения/удаления чужой заметки должны отклоняться с HTTP 409.
   Удалите свою тестовую заметку и проверьте удаление элемента инфоблока.

Если карточки не загружаются, проверьте JSON-ответы запросов `job/load` и
`plan/load`, `memo/load`, ID в конфиге и коды свойств. Пустой список без ошибки тоже может
означать неверный ID, ответственного или период.

Для существующего развёртывания заметок также обязательно задайте
`BXDASH_MEMO_IBLOCK_ID` явно: прежний зашитый ID `92` больше не используется.
Публикуйте обновлённый `back/app/ctl/controller_memo.php` вместе с настройкой
`back/conf.php`; пересборка frontend не нужна. Инфоблок создаётся вручную
после согласования, изменения структуры БД код не выполняет.

Соседний тип `absent` пока использует зашитый ID `3` и не входит в эту настройку.

## Проверка кода без портала

```sh
php tools/iblocks-test.php
php tools/iblocks-test.php custom
php tools/iblocks-test.php invalid
```

Проверки с подставным API Bitrix покрывают отсутствие настройки, свои ID, фильтры чтения,
создание, запись свойств работы, запрет изменения/удаления чужого элемента
и отказ при некорректной конфигурации.
Они не создают инфоблоки и не заменяют проверку на целевом портале.
