# Колонки на старом и новом Bitrix

Backend поддерживает два провайдера с общим REST `stage/*`. Frontend и модель
`DashItem.stages` не зависят от выбранного хранилища.

В серверном `conf.php` рядом с `api.php` задайте:

```php
// Новый Bitrix: существующий личный «Мой план» и штатные привязки задач.
$stagesProvider = 'bitrix';
```

Допустимые режимы:

| Значение | Поведение |
| --- | --- |
| `bitrix` | Штатные личные стадии и привязки задач. При отсутствии API — ошибка, без переключения хранилища |
| `table` | Прежние таблицы `bxdash_stage` и `bxdash_item_stage` |
| `auto` или настройка отсутствует | `bitrix`, если доступны классы `StagesTable` и `TaskStageTable`; иначе `table` |

Если новый портал уже использует собственные колонки bxDash и нужно продолжить
работать с ними, явно оставьте `table`. Автоматического переноса данных между
провайдерами нет. При переходе `table → bitrix` отображаются штатные колонки и
привязки нового портала; прежние строки `bxdash_*` сохраняются.

## Что использует штатный провайдер

- Стадии — `Bitrix\Tasks\Kanban\StagesTable`, только
  `ENTITY_TYPE=WORK_MODE_USER` (`U`), `ENTITY_ID` — ID владельца доски.
- Стадия по умолчанию — `SYSTEM_TYPE=NEW`.
- Привязки задач — `Bitrix\Tasks\Kanban\TaskStageTable`, с владельцем через
  связь `STAGE.ENTITY_ID`. Изменение личного плана не меняет проектную стадию задачи.
- `P` — временная шкала, `G` — проект, `A` — активный спринт. Эти колонки и
  привязки не используются провайдером личного плана.
- Стопки bxDash и привязки jobs/tickets — `CUserOptions`, категория
  `bxdash_kanban`, имя `native_board`, отдельно для каждого владельца доски.
  Эти данные видны в bxDash; стандартный UI Bitrix работает со своими задачами.

У нового провайдера нет SQL-миграций, новых таблиц или полей. `install()` только
проверяет наличие API. Если у пользователя пока нет личного плана, при первом
открытии его владельцем или администратором колонки создаёт штатный
`StagesTable::getStages()`. Предыдущий режим Bitrix восстанавливается после вызова.
Старый провайдер `table` сохраняет прежний механизм установки своих таблиц.

Менять личную доску может её владелец или администратор. Перед переносом задачи
дополнительно проверяется доступ к ней через `CTaskItem::GetData()`. Удаление
колонки переносит элементы в выбранную колонку этого же владельца; колонку
`NEW` удалить нельзя. Ошибки ORM передаются клиенту, связанные изменения
порядка и переноса/удаления выполняются в транзакции.

## Публикация и проверка

Обновите оба файла backend:

1. `back/app/models/stages_provider.php` — выбор режима.
2. `back/app/models/stages_provider_bitrix.php` — штатный провайдер.

Сохраните остальные настройки `conf.php`, добавьте `$stagesProvider = 'bitrix';`
и перезагрузите dashboard. Пересобирать frontend для этой правки не требуется.

Проверьте под владельцем доски:

1. `api/stage/list/1229` возвращает колонки существующего личного плана
   (на проверенном портале — `5168` «Не спланированы», `5169` «Сделаю на неделе»).
2. После перезагрузки карточки стоят в тех же личных колонках, что в Bitrix.
3. Перенос тестовой задачи в bxDash отражается в стандартном «Моём плане»
   после его обновления. Обратный перенос отражается в bxDash после перезагрузки.
4. Создание, название, цвет, порядок и удаление тестовой колонки отражаются
   в обоих интерфейсах. При удалении явно проверьте перенос тестовой карточки.
5. Стопки и размещение тестовой работы/заявки сохраняются после перезагрузки bxDash.

Штатный интерфейс Bitrix не отправляет события в WebSocket bxDash:
для проверки синхронизации используйте перезагрузку или дождитесь опроса задач.

## Локальные проверки без портала

```sh
php tools/stages-test/test_bitrix_provider.php
php tools/stages-test/test_provider_selection.php legacy
php tools/stages-test/test_provider_selection.php modern
php tools/stages-test/test_provider_selection.php explicit-table
php tools/stages-test/test_provider_selection.php missing-native
```

Тесты используют подставной API, проверяют изоляцию `U` от `P/G`, сохранение
чужого плана и проекта при переносе, CRUD, стопки, jobs/tickets, права и откат
при ошибке. Они не подключаются к БД. Реальные создание/перенос и отображение
в стандартном UI требуют проверки на целевом портале.
